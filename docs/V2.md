# ditto-chaos v2: scenarios, agents, autonomy

This document describes what version 2 adds on top of the Day 1/Day 2 code, how it is
kept safe, and exactly how far each part has been verified. The original single-fault
CLI (`guard.py`, `main.py run`) still works unchanged.

## Verification levels used in this document

| Label | Meaning |
|---|---|
| **mocked** | Covered by `python -m pytest -q`; Docker, Ditto and the AI provider are replaced by fakes. |
| **real Docker** | Passed `tests/integration/test_real_docker.py` against a real daemon on a throwaway `alpine` container (never the Ditto services). Opt-in; re-run it on your machine. |
| **live** | Observed once against the real local Ditto stack through the HTTP API (2026-10-10). One run is an observation, not a guarantee. |
| **not verified** | Implemented and unit-tested, but never observed outside mocks. |

## Module map

```
faults.py            fault registry: 9 fault classes + 3 explicitly unsupported entries
scenario.py          multi-fault engine: validate() / preflight_check() / ScenarioRun, journal, lockout
controller.py        operating modes, sandbox checks, the autonomous loop
agents.py            7 agents + the coordinator that runs them and persists each run
scenario_planner.py  schema-2.0 proposals (model picks among pre-validated candidates)
learning.py          observe / predict / compare / rank_candidates -- deterministic, no model
store.py             SQLite knowledge store (experiments, learning, recommendations, agent runs, timeline, audit)
events.py            in-process event bus behind GET /api/stream (SSE)
monitor.py           server-side monitor: probe files + docker ps/stats -> events
orchestrator.py      (extended) start_scenario(), post-run pipeline, shutdown, lockout resolution
api.py               (rewritten) v2 endpoints; every legacy endpoint kept
frontend/            (rewritten) 7 pages on one snapshot + SSE stream
```

## Operating modes

Set with `AUTONOMY_MODE` (default `recommend`), changeable at runtime from the dashboard
or `POST /api/controller/mode`. The mode is always shown in the dashboard header.

| Mode | What can inject a fault |
|---|---|
| `observe` | Nothing. Every run request is refused (HTTP 403). |
| `recommend` | An operator may authorize a scenario the planner **proposed**. Custom scenarios are refused. |
| `manual` | An operator may also author and authorize a custom scenario. |
| `autonomous_sandbox` | The controller loop runs proposed scenarios itself, inside the sandbox policy. |

`autonomous_sandbox` cannot be selected unless `AUTONOMY_SANDBOX_ENABLED=true` is in the
process configuration -- the API and dashboard cannot turn it on by themselves. Before
**every** autonomous experiment the controller re-runs these checks and stops the loop
(no retry) if any fails: sandbox flag set, `DITTO_URL` is loopback, policy non-empty, no
recovery lockout, Docker reachable, every allowed target running, baseline present/healthy/
fresh, live health fresh and healthy. The loop also stops itself on any refusal and on any
run that did not end `COMPLETED` + `recovered`, and after `AUTONOMOUS_MAX_EXPERIMENTS`.

What a model can never do: no model output is an authorization (an `Authorization` object
is only ever built by `controller.operator_authorization()` or `controller._autonomous_grant()`),
no model output reaches a shell, and the planner can only pick one of the candidates that
`scenario.validate()` already accepted. Stop conditions, limits and rollback are code.

*Verification:* modes, checks and the loop are **mocked**. The autonomous loop has **not**
been run against real Ditto.

## Fault types

`python main.py faults` or `GET /api/faults` prints this from the registry.

| Fault | Mechanism | Parameters (bounds) | Rollback verified by | Status |
|---|---|---|---|---|
| `kill` | `docker kill <id>` | -- | container running (same id, or service observed under a replacement) | mocked, real Docker |
| `stop` | `docker stop -t` | `grace_s` 1-30 | same | mocked, real Docker |
| `restart` | `docker restart -t` | `grace_s` 1-30 | same | mocked, real Docker |
| `pause` (dependency unavailable) | `docker pause` / `unpause` | -- | not paused, running | mocked, real Docker |
| `delay` | `tc netem delay` via netshoot helper | `delay_ms` 1-5000, `ttl_s` 5-600 | `tc qdisc show` has no netem | mocked, real Docker, **live** |
| `jitter` | `tc netem delay D J` | `delay_ms` 1-5000, `jitter_ms` 1-2000 (<= delay) | same | mocked, real Docker |
| `loss` | `tc netem loss` | `loss_pct` 1-100 | same | mocked, real Docker, **live** |
| `bandwidth` | `tc netem rate` | `rate_kbit` 8-100000 | same | mocked, real Docker |
| `cpu_throttle` | `docker update --cpu-quota` | `cpu_pct` 5-90 | CpuQuota restored | mocked, real Docker |
| `cpu_stress` | -- | -- | -- | **not supported**: needs a load generator inside the target's cgroup |
| `memory_pressure` | -- | -- | -- | **not supported**: would OOM-kill a JVM; not bounded or reversible |
| `request_failure` | -- | -- | -- | **not supported**: needs a proxy in the request path |

Every mutating command addresses the container by its full 64-character id. Network
faults carry a dead-man's switch (`ttl_s`): the helper removes the rule itself even if
this process dies. `pause`, `kill`, `stop` and `cpu_throttle` have no such switch; they
rely on the recovery journal (below).

## Multi-fault scenarios

A scenario is a list of actions (`fault`, `target`, `params`, `start_offset_s`,
optional `duration_s`) plus `max_duration_s`. Example (`python main.py scenario file.json`
validates it without injecting):

```json
{"name": "slow search, lossy connectivity", "max_duration_s": 20,
 "actions": [{"fault": "delay", "target": "things-search", "params": {"delay_ms": 300}},
             {"fault": "loss", "target": "connectivity", "params": {"loss_pct": 5}, "start_offset_s": 4}]}
```

`scenario.validate()` refuses the **whole** plan before anything is touched if any of
these fail: unknown/unsupported fault, target not allowlisted, parameter out of bounds
(rejected, never clamped), duplicate action, two faults on one target (except netem +
cpu_throttle), a cross-target combination outside the tested allowlist, or a limit.

Tested combinations (by fault category, different targets): network+network,
network+process, network+resource, process+resource. Two process faults on two services
at once (`kill` + `pause`, ...) is refused.

| Limit (env var) | Default |
|---|---|
| `MAX_ACTIVE_FAULTS` | 3 concurrently |
| `MAX_AFFECTED_SERVICES` | 2 |
| `MAX_SCENARIO_DURATION_S` | 300 |
| `MAX_CUMULATIVE_INTENSITY` | 1.6 (kill/stop/pause = 1.0, restart 0.6, delay = ms/5000, loss = pct/50, ...) |

Execution order is by `start_offset_s`. Rollback order restores the most depended-on
service first (dependency-map fan-in), ties in reverse order of application.

### What the engine guarantees (and how)

1. **Atomic preflight.** Every target is resolved and every fault's read-only preflight
   passes before the first mutation.
2. **Locks.** One scenario lock plus one lock per target; a `guard.py` CLI run on the same
   target blocks a scenario and vice versa.
3. **Journal before mutation.** Recovery info (container id, helper name, original CPU
   quota) is written to `state/journal/<id>.json` before the first command and before
   every apply.
4. **Uncertain is not failed.** If an apply errors or times out, the engine inspects the
   real state, never retries the mutation, and rolls it back.
5. **Roll back everything, independently.** Every action that is not `pending` is rolled
   back; one failure never stops the others. Rollback is idempotent.
6. **Verified, not assumed.** An action counts as reverted only after its clean state is
   observed; every affected target is then checked again independently.
7. **Kill switch.** Same `guard.check_breach()` as v1, every tick, driven by the engine's
   own in-process probe: it does not depend on `probe.py`, the monitor, or a browser. A
   probe that hangs counts as a failed tick, so losing monitoring trips the switch.
8. **Emergency stop** (`POST /api/stop`, dashboard button) rolls back every active fault.
9. **Cancellation/shutdown.** The API's shutdown waits for the running experiment's
   rollback. A cancelled task still rolls back (shielded) and returns a record.
10. **Crash recovery.** On startup the API replays any journal left by a dead process;
    `python main.py recover` does the same from the CLI.
11. **Lockout.** If any rollback cannot be verified the run ends `RECOVERY_REQUIRED`,
    `state/recovery_required.json` is written with the manual commands, and every new
    injection (CLI scenario path, API, autonomous loop) is refused with HTTP 423 until
    it is resolved.

*Verification:* all of the above are **mocked** (see `tests/test_scenario.py`). One
two-fault scenario (`delay@things-search` + `loss@connectivity`, 20 s) was run **live**:
both applied, search latency degraded, both rollbacks verified, recovery in ~2 s, and
`tc qdisc show` on both containers was confirmed clean by hand afterwards. Lockout,
crash recovery and emergency stop have **not** been exercised against real Docker.

### Resolving `RECOVERY_REQUIRED`

1. Read the banner / `GET /api/recovery`: it lists each unverified fault and the exact
   manual command.
2. Fix the cause (usually: Docker was unreachable, or a helper image is missing), then
   press **Retry verified recovery** (`POST /api/recovery/resolve`, or `python main.py recover`).
   This re-runs the idempotent rollback and clears the lockout only if the clean state is
   observed.
3. If you repaired it by hand and verification still cannot pass, clear it with a note:
   `POST /api/recovery/resolve {"force": true, "note": "..."}`. This is audited.

## Agents

A lightweight coordinator (`agents.Coordinator`), no framework. Agents never call each
other; the coordinator runs them in a fixed order and passes validated outputs forward.
Every invocation is persisted (agent, version, status, timings, attempts, error,
evidence ids, provider) and published to the event stream.

| # | Agent | Kind | Responsibility | Pipeline |
|---|---|---|---|---|
| 6 | `risk` | deterministic | Transitive blast radius per service; flags services with no evidence | plan 1 |
| 1 | `fault_injection` | hybrid | Proposes a scenario: ranks candidates, model may pick one and adjust params; re-validated | plan 2 |
| 2 | `recovery` | deterministic | Recovery state machine, one automatic rollback retry, recovery report | post-run 1 |
| 7 | `validation` | deterministic | Is the run conclusive? Only conclusive runs count as evidence | post-run 2 |
| 3 | `insights` | hybrid | Findings from before/fault/recovery windows; labels each `measured` or `hypothesis` | post-run 3 |
| 4 | `learning` | deterministic | Stores the case, checks the prediction, re-ranks, re-tests implemented recommendations | post-run 4 |
| 5 | `remediation` | hybrid | Maps each finding to an engineering change with evidence, risk and a re-test | post-run 5 |

"Hybrid" = uses the LLM when `AI_ENABLED=true` and the call succeeds, otherwise a
deterministic fallback, and the run is then recorded as `fallback`, not `completed`.
Execution of faults, stopping and rollback are **not** agent work: they are
`scenario.ScenarioRun`. The recovery *agent* reports on and retries what that code did.

Statuses are independent: `completed`, `fallback`, `failed`, `timeout`, `skipped`. If
`insights` fails, `learning` still stores the run and `remediation` is `skipped` with the
reason. The orchestrator status always ends `done` or `error`.

Recovery states: `RECOVERY_NOT_REQUIRED`, `FAULTS_ACTIVE`, `STOP_REQUESTED`,
`ROLLBACK_IN_PROGRESS`, `VERIFYING_RECOVERY`, `RECOVERED`, `HEALTH_NOT_CONFIRMED`
(faults verified removed, health did not return in time), `RECOVERY_REQUIRED`.

Why two extra agents: `risk` gives the planner real blast-radius data, and `validation`
is what stops a 1-tick or unverified run from being counted as learning. Considered and
left as future work: anomaly detection on live telemetry, a resilience score, and a
separate supervisor (its duties -- timeouts, retries, status, fallback -- are in the
coordinator).

*Verification:* **mocked** (`tests/test_agents.py`). The post-run pipeline ran **live**
once with the AI provider unavailable (HTTP 429 quota), i.e. on the deterministic
fallback. The LLM paths have only been exercised with a stubbed provider.

## How learning works (exactly)

There is no trained model. `GET /api/learning` reports `trained_model: false`.

1. `learning.observe(record)` reduces a record to measured effects and symptom labels:
   latency ratio >= 1.5x baseline, error rate +5 points, staleness +5 s, any lost update,
   any search drift, recovery >= 60 s or timed out. Missing measurements produce no symptom.
2. A run is **evidence** only if a fault was really injected, it was not a dry run, and
   the validation agent judged it `conclusive`.
3. `predict()` states the expected outcome from prior evidence of the same scenario
   (or the same fault/target), with the sample size (`"3 of 4"`), never a percentage.
4. `compare()` checks that prediction against the outcome after the run.
5. `rank_candidates()` scores each valid candidate:

   `score = 0.30*novelty + 0.20*outcome_uncertainty + 0.20*usefulness + 0.15*relevance + 0.15*follow_up - 0.40*repetition_penalty`

   - novelty = 1/(1+runs of this scenario)
   - outcome_uncertainty = 4p(1-p), p = (informative runs + 1)/(runs + 2)
   - usefulness = (informative related runs + 1)/(related runs + 2)
   - relevance = normalised fan-in of the targets
   - follow_up = 1 when an `implemented` recommendation from this scenario awaits a re-test
   - repetition_penalty = 1 when the last two runs ended the same within 7 days
   - a scenario with any unverified rollback in its history is **blocked** from selection
6. Each run's learning record stores the score and rank of its scenario before and after,
   and whether the top candidate changed. That stored delta is the "influence".
7. A recommendation moves `proposed -> accepted -> implemented` by operator action. The
   next evidence run of the same scenario marks it `verified` (finding did not recur) or
   `not_effective` (it did). Nothing is ever applied by this tool.

## Real-time pipeline

- `GET /api/snapshot` returns the full state plus `seq`/`boot`; `GET /api/stream?last_seq=&boot=`
  (Server-Sent Events) then delivers `{v, boot, seq, ts, type, data}` events from that point.
- Reconnect replays missed events from a bounded ring; a gap, a server restart (`boot`
  changed) or an overflowed client queue yields a `resync` event (re-fetch the snapshot).
- Publishing never blocks; a slow client only loses its own events and is told to resync.
- The dashboard loads the snapshot first, dedupes by `seq`, caps history at 1800 rows,
  reconnects with exponential backoff (1 s -> 30 s, jittered), and labels the target
  `STALE`, `UNKNOWN` or `DISCONNECTED` instead of `HEALTHY` whenever the data is not a
  fresh, connected measurement.
- Monitoring health (`ok`/`stale`/`down`) is reported separately from target health.

## Activity log

`activity.py` adds an `events` list to every experiment record (guard.py records are now
schema 1.1; scenario records stay 2.0, the field is additive). Each event is
`{seq, ts, t_s, state, kind, message, detail}` with `kind` one of `info`, `command`,
`health`, `decision`, `warning`, `error`. `seq` increases by one per event and is never
reset; at most 2000 events are kept per experiment (oldest dropped first).

- **Recording only.** `activity.emit()` cannot raise into its caller, and no decision reads
  an event. Kill-switch logic and thresholds are unchanged.
- **Commands are reported by `guard.run_cmd` itself**, through an experiment-scoped observer
  (or an explicit `on_command` argument), so a `command` event says what happened: executed
  with its exit code and error output, timed out, or not executed (dry run).
- **Secrets.** Configured values of `API_TOKEN`, `GEMINI_API_KEY` and a non-default
  `DITTO_PASS`, plus `key=`/`token=`/`password=` pairs and authorization headers, are
  redacted from messages and details; long text is truncated.
- **Dry run.** `POST /api/scenarios/run {"dry_run": true, "scenario": ...}` (or the
  builder's button) runs the lifecycle with real health probes, synthetic targets and no
  Docker contact. Apply commands are captured as exact argument vectors; rollback steps
  are shown as descriptions. It takes no lock, needs no authorization, is allowed in any
  mode and during a lockout, skips the agent pipeline, and is never evidence.
- **API.** `GET /api/experiments/{id}/events?after_seq=N` returns events with `seq > N`
  for the running experiment (from memory) or a saved record, plus `running`, `terminal`,
  `dry_run` and `last_seq`. 404 for an unknown id, 422 for a negative or non-integer
  `after_seq`, an empty list for records that predate the log.

*Verification:* **mocked** (`tests/test_activity.py`, 35 tests; frontend 14 tests). One
dry run was observed **live** through the API: 28 events, 0 commands executed, and the
Docker container list was identical before and after. The log of a real fault run has only
been produced under mocks so far. The component was viewed in a real browser for a dry run
and for saved records.

| `POST /api/plan`, `GET /api/plan` | run the planning agents; current proposal |
| `POST /api/scenarios/run` | start (`authorize: true` + `scenario` or `proposal_id`, optional `request_id`) |

| `GET /api/agents`, `/api/agents/runs` | live agent state; persisted runs |
| `GET /api/recovery`, `POST /api/recovery/resolve` | lockout and journals; resolve |

Status codes: 400 refused, 401 bad token, 403 mode forbids, 409 conflict (already running,
stale proposal), 422 invalid input or policy violation (`errors[]`), 423 recovery required,
503 knowledge store unavailable. Set `API_TOKEN` to require `X-API-Token` on every `/api`
route (reads included; `/api/livez` and `/api/readyz` stay open). `POST /api/stream/ticket`
returns the single-use ticket a browser passes to `/api/stream`. When `frontend/dist` exists,
every non-`/api` path serves the built dashboard.

## Known limitations

- The autonomous loop, lockout, crash-journal replay and emergency stop are **mocked only**.
- Only gateway-level direct-read and search probes are measured. There are no per-service
  internal metrics, so any root cause below the API is a hypothesis and is labelled as one.
- CPU/memory figures come from `docker stats` every ~10 s; they are context, not a safety signal.
- `pause`/`kill`/`stop`/`cpu_throttle` have no dead-man's switch. A hard crash of the API
  leaves them in place until the next start replays the journal (or `python main.py recover`).
- `tc` rules this tool did not create are detected and refused only on the root qdisc of `eth0`.
- Token auth is a single shared secret, not per-user roles. The `X-Operator` header is a
  self-declared name for the audit log. With a token set, every `/api` route needs it
  except the two health probes; the stream uses a single-use ticket.
- The LLM paths (planner choice, analysis) were not exercised live: the configured Gemini
  key returned HTTP 429 (quota exceeded) during verification.
- The dashboard was checked in headless Chromium (`npm run e2e`): every page, a preview,
  a dry run and its activity log, with no console errors. That check drives a dry run only;
  the UI during a REAL fault run (emergency stop, recovery-required banner) is covered by
  component tests, not by a browser.
- Agent timeouts abandon a thread-based agent call rather than killing it.
